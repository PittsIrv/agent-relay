## 1. Correctness risks

1. **Blocker: a delayed attachment can still close the PR restored by a failed `take`.** Suppose PR P belongs to epoch N. Failed `take` restores P but rebinds it to epoch N+1. A delayed `attach_pr(..., epoch=N, number=P)` now fails the idempotence check, records P as superseded, and causes `_open_pr` to retire it—even though P is the current PR. The new tests cover restoration and repeated attachment separately, not this combination.  
   **Evidence:** `tasks.py`: `task["pr_epoch"] = task["epoch"]`; the attachment exemption requires `task.get("pr") == number and task.get("pr_epoch") == epoch`; rejection records `event(task, "superseded", worker=worker, epoch=epoch, retired_pr=number)`. `conversation.py` then calls `self._retire(number, task)`.

2. **Blocker: the “landed push is never applied twice” fix fails if another writer advances the branch before the recovery check.** Writer A successfully pushes commit C but receives a local failure; writer B then pushes a successor D. A’s `ls-remote` observes D, not C, so the code reports contention and may rerun an already-committed mutation. The documented mutation contract requires absence of external side effects, not idempotence.  
   **Evidence:** `gitstore.py`: `if latest_sha == sha: return True`, followed by `if latest_sha != parent: return False`; `change` documents that `mutate may run again on contention`.

3. **An explanatory retirement comment is permanently lost if closing succeeds but commenting fails.** On retry, the PR is closed, so `_retire` skips the comment. Closing first prioritizes the important safety action, but it does not provide eventual delivery of everything unfinished.  
   **Evidence:** `conversation.py`: `if pull.get("state") == "open" and not pull.get("merged"):` gates both `self.gh.close_pr(number)` and the subsequent `self.gh.comment(...)`.

## 2. Hidden assumptions

1. **Rollback assumes nobody has already acted on retirement information published during the hold.** Removing `retired_pr` from state cannot invalidate another process’s existing snapshot or undo a GitHub close. Deferring the taking process’s own posts is insufficient unless other flushers are also prevented from retiring a rollback-eligible PR. That exclusion is not established here.  
   **Evidence:** `tasks.py`: `if ev["kind"] == "held" and ev.get("epoch") == epoch: ev.pop("retired_pr", None)`; adjudication: “`take` posts only after success.”

2. **PR adoption assumes the head branch uniquely identifies the intended attempt and acceptable PR.** Excluding closed-unmerged PRs addresses the stated filtering bug, but the shown selection does not validate base branch, expected commit, or an attempt marker. Whether those checks are unnecessary depends on branch-identity invariants absent from this package.  
   **Evidence:** `github.py`: `head=f"{owner}:{branch}", state="all"` and `return usable[0] if usable else None`.

3. **Durable retirement still assumes the responsible worker returns.** Persisting an event is not equivalent to guaranteeing that some available collaborator will execute it. This is explicitly accepted in the adjudication, but the broader “next run” recovery wording needs that qualification.  
   **Evidence:** adjudication 2.4: “Retirement depends on the acting worker returning → **agree, accepted limit**”; architecture: unfinished work is “finished on the next run.”

4. **The thread-safety argument assumes unlocked reads cannot interfere with local Git bookkeeping.** The supplied change serializes `Store.change`, not visibly all access to shared local Git state. Without `Store.read` and the remaining implementation, this assumption cannot be checked; it is not evidence of a specific read race by itself.  
   **Evidence:** `gitstore.py`: `with lock: return self._change(mutate)` appears inside `change`; architecture says the heartbeat and GitHub threads “share the clone’s state store.”

## 3. Design decisions I would challenge

1. **Retirement authorization should not follow solely from an epoch mismatch.** I would weigh an explicit hold/retirement lifecycle that protects both the current PR and any rollback-eligible PR, and only authorizes irreversible closure after supersession is committed. Merely adding a current-PR check would not settle the overlapping-hold case.  
   **Evidence:** `tasks.py` records `retired_pr=number` whenever the attachment fails its epoch/status/occupied-slot conditions.

2. **Push-outcome recovery should recognize committed operations, not just an unchanged remote tip.** I would weigh durable mutation IDs, or ancestry-aware recognition under a documented append-only state-history invariant. Either approach must distinguish contention-before-commit from advancement-after-commit.  
   **Evidence:** `gitstore.py`: `if latest_sha == sha: return True  # Pushed; only a local bookkeeping step failed. Never apply twice.`

3. **Rejected attachment should also have an idempotence key.** Repeating the same stale attachment currently appends another historical PR entry and another retirement event. I would weigh one durable retirement record per task/attempt/PR, with delivery state separate from its creation.  
   **Evidence:** `tasks.py`: `task.setdefault("past_prs", []).append({"pr": number, "epoch": epoch})` and the unconditional `event(..., "superseded", ...)` on each refusal.

4. **Close delivery and comment delivery should have separate semantics.** I would either track the explanatory comment independently with a marker or explicitly document it as best-effort. Using the PR’s closed state as the comment’s implicit acknowledgement loses comments after partial success.  
   **Evidence:** `conversation.py`: `self.gh.close_pr(number)  # Close first: a retried close never comments twice.`

## 4. What a skeptical PI or senior engineer would ask first

1. **Can the rollback test delay an old-epoch attachment until after `unhold`, then verify that the restored PR remains open and has no retirement event targeting it?** The current rollback test flushes the restored snapshot, which does not exercise the stale producer.  
   **Evidence:** `test_failed_take_of_a_reviewed_task_keeps_its_pr_live`: `self.talk(self.a).flush(after)`.

2. **Can the push-recovery test inject a landed-but-reported-failed push, let an independent clone advance the branch, and prove the original mutation is committed exactly once?** This is the missing interleaving for the new success-detection branch.  
   **Evidence:** `gitstore.py`: success recovery depends on `latest_sha == sha`.

3. **What prevents a retirement already read from a hold event from executing after rollback?** The answer needs an exclusion or authorization mechanism, not merely removal of the event field from the latest state.  
   **Evidence:** `tasks.py`: `ev.pop("retired_pr", None)  # Nothing to close: the PR was restored.`

4. **Where is the successful slow-GitHub trace across two workers, including epoch changes while the call is outstanding?** Failure-only slow-call coverage does not exercise successful external side effects arriving after state has advanced.  
   **Evidence:** adjudication 4.2: “a successful slow `gh` stand-in is future test work”; 4.4: “Real two-machine trace → **open**.”

## 5. Documentation gaps

1. **The package does not contain enough implementation context to verify the claimed deferred posting and retirement acknowledgement behavior.** The bodies of `interactive.take`, `Conversation.flush`, and the complete store read/write path are needed to audit those guarantees; references to files elsewhere are not supplied implementation.  
   **Evidence:** adjudication claims “`take` posts only after success,” but the supplied diff contains no `interactive.py` implementation; the shown conversation excerpt ends with `def flush_all(self, state):` and its loop header.

The unconditional message also exceeds the comment-delivery behavior shown above.  
   **Evidence:** `worker.py`: `self._syncing.join(timeout=120)` followed by “anything unfinished is posted on the next start”; adjudication accepts acting-worker-dependent retirement.
