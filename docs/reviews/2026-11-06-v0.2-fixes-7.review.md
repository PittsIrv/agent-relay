## 1. Correctness risks

1. **The new lock does not prevent stale configuration from corrupting the interactive workflow.** Configuration is passed into the wrapper before it acquires the lock and is not reloaded afterward. Two invocations can therefore serialize execution while using the same old configuration. For example, `take` can finish switching branches and recording a hold; a waiting `handoff`, using configuration loaded before that take, sees no hold, creates a separate task, and writes an empty hold map.
   **Evidence:** `with one_at_a_time(repo): return _handoff(repo, cfg, store, **kwargs)`; `held = (cfg.get("held") or {}).get(branch or "")`; `config.update(repo, held={k: v for k, v in (cfg.get("held") or {}).items() if k != branch}, ...)`.

2. **A capped superseded-PR thread can still indefinitely block closing later superseded PRs on the same task.** `_retire` closes one PR and then scans its comments. If that scan raises on the cap, execution exits the entire retirement loop. On subsequent flushes, the same already-closed PR’s comment scan fails again, preventing later retirements. The added test covers a capped task-issue thread, not this case.
   **Evidence:** `for ev in pending: ... self._retire(ev["retired_pr"], task)`; inside `_retire`, `self.gh.close_pr(number)` precedes `self.gh.issue_comments(number)`; exception containment is around the whole `_flush` call.

3. **The offline GitHub fix incorrectly disables label filtering for `state=all`.** Python evaluates `and` before `or`, so every issue passes when `wanted == "all"`, regardless of its labels. Adoption tests using this stand-in can therefore succeed where GitHub would not, including for manually unlabelled orphans.
   **Evidence:** `if wanted == "all" or i["state"] == wanted and (not label or any(l["name"] == label for l in i["labels"]))`.
   The intended predicate is `(wanted == "all" or i["state"] == wanted) and (...)`.

## 2. Hidden assumptions

1. **The concurrency fix assumes callers provide configuration that remains current through lock acquisition.** No such contract or enforcement appears in the supplied wrappers.
   **Evidence:** `def take(repo, cfg, store, task_id, emit=print):` passes the supplied `cfg` unchanged into `_take` after acquiring the lock.

2. **Eventual PR retirement depends on the worker responsible for the event returning to flush it.** Other workers do not adopt that responsibility, so retirement is not guaranteed merely because another supervisor remains online.
   **Evidence:** Pending events require `ev.get("worker") == self.worker`; the adjudication says, “a shared queue stays out of scope.”

3. **The locking guarantee depends on mutations going through cooperating entry points.** It does not protect against ordinary Git operations or an editor changing the working tree during handoff.
   **Evidence:** The lock is an advisory `fcntl.flock` on `interactive.lock`; handoff separately reads `HEAD` and takes snapshots afterward. The documented guarantee should remain narrowly about relay commands, not working-tree isolation.

## 3. Design decisions to challenge

1. **Challenge acquiring the interactive lock after loading mutable configuration; weigh loading it inside the critical section.** Otherwise the lock protects execution order but not the read–modify–write transaction over `held` and `handed_off`.
   **Evidence:** `_take` builds its update from `cfg.get("held")`, and `_handoff` builds both configuration maps from the supplied `cfg`.

2. **Challenge coupling safety-critical PR closure to retirement-note delivery; weigh separate closure and annotation passes.** Close every eligible PR first, with failures contained per PR, and only then attempt deduplicated notes. This does not require introducing a shared queue.
   **Evidence:** `_retire` performs both `self.gh.close_pr(number)` and the capped comment-marker scan before returning to the next retirement.

3. **Challenge using an untested stand-in change as the last adjustment before release; weigh explicit API-contract tests for state and label combinations.**
   **Evidence:** “The full suite (60 tests) passed locally before a one-line fix to the offline GitHub stand-in”; the supplied change contains the precedence error identified above.

## 5. Documentation gaps

1. **The package does not establish when CLI and hook callers load configuration relative to lock acquisition.** Their entry-point source and `config.update` semantics are needed to verify the claimed concurrency fix end to end.
   **Evidence:** The supplied functions begin with `handoff(repo, cfg, store, **kwargs)` and `take(repo, cfg, store, task_id, ...)`, and later call `config.update(...)`; those surrounding implementations are absent.

2. **The retirement guarantee is broader than the supplied implementation supports.** Documentation needs to distinguish task-thread caps from retired-PR-thread caps and state the responsible-worker availability requirement.
   **Evidence:** Architecture text says closing superseded PRs “is never blocked by” duplicate checks, but `_retire` performs its own comment scan inside the retirement loop.

3. **The package does not supply the pagination implementation needed to independently verify exception containment.** The adjudication asserts containment, but the exception type raised at the cap is not shown.
   **Evidence:** `flush` catches a specific tuple of exception classes; `labeled_issues` delegates to `self.pages(...)`, whose implementation is omitted.

## 6. What is done well

1. **The checkpoint update now directly removes inherited verification when no replacement check accompanies it.**
   **Evidence:** `if verification is None: task.pop("verification", None)`, with an end-to-end hand-back regression.

2. **Separating result identity from lease identity resolves the demonstrated rollback-token reuse problem.**
   **Evidence:** `hold` increments `task["epoch"]`, `unhold` no longer restores it, and the new test rejects the first hold token after a second hold.

3. **Retirement now precedes task-issue comment deduplication, fixing the specific capped-task-thread failure.**
   **Evidence:** The retirement loop precedes `self.gh.issue_comments(task["issue"])`, and the added regression asserts that the old PR closes.

**do not ship** — The verification and monotonic-epoch fixes address their demonstrated failures, but the claimed concurrency fix still permits stale-configuration task duplication and lost hold mappings, and retirement remains vulnerable to same-task starvation through a capped PR thread. Fix those paths, correct the stand-in predicate, and run targeted regressions plus the full suite on the final revision; documenting alpha limits does not substitute for those corrections.
