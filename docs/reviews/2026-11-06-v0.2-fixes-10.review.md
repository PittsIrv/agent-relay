## 3. Design decisions I would challenge

1. **I would separate the courtesy-note receipt from remote closure reconciliation.** Keep checking whether historical PRs are open, while using a receipt only to avoid repeating notes. If repeated API reads are considered too costly, explicitly define reopening as unsupported and document the resulting manual recovery requirement.
   **Evidence:** `_reconcile_retired` uses the same `handled` receipt to bypass both `_close_superseded` and `_note_superseded`.

2. **I would eliminate the separate, exception-propagating retirement path.** After a refused attachment, reconcile the refreshed durable task through the same failure-isolated machinery, rather than maintaining two different cleanup semantics.
   **Evidence:** `_reconcile_retired` catches `DEFERRABLE` per PR, whereas `_retire` calls close and note without that isolation.

3. **I would distinguish closure failures from note or receipt failures in diagnostics.** The present message can report deferred closing when the PR is already closed and only its explanatory comment failed.
   **Evidence:** `self.emit(f"Closing superseded PR #{number} deferred: {exc}")` surrounds closure, note posting, and receipt persistence.
