# Independent review — 2026-11-07 00:02

## gemini-3.1-pro-preview

1. Correctness risks
1. A network error while notifying a user of a refused `/relay cancel` will permanently drop the notification because the command is still marked as applied. 
   Evidence: `conversation.py` lines 360-362 (`except RelayError: pass` followed immediately by `applied.append({"task": task_id, "verb": words[1], "by": login, "result": result})`).
2. A task that reached the "review" status but lacks a recorded PR (e.g., due to a previous GitHub API error) completely bypasses the ownership check, allowing anyone to cancel it. 
   Evidence: `tasks.py` line 313 (`reviewed = task["status"] == "review" and task.get("pr")`), which falls through to unprotected cancellation if `pr` is missing.

2. Hidden assumptions
1. The codebase assumes `task.get("requested_by")` is always a string type. 
   Evidence: `tasks.py` line 301 (`return (by or "").lower() == owner.lower()`), which will raise an `AttributeError` and crash if `owner` is somehow parsed as a dict, list, or other object.

3. Design decisions you would challenge, and the alternative you would weigh
1. Silently swallowing `RelayError` when sending a refusal notification. I would weigh removing the `try...except RelayError: pass` block entirely, letting the error propagate so the sync loop fails and retries, guaranteeing the human actually receives the rejection message instead of experiencing silent failure.
   Evidence: `conversation.py` lines 358-361.
2. Hardcoding a strict owner-only cancel rule without a fallback. I would weigh adding a check for repository admins or maintainers to ensure PRs aren't permanently deadlocked if the original task owner leaves the team or is unavailable.
   Evidence: `tasks.py` lines 298-303 (`may_cancel_reviewed` only validates against `requested_by` or `created_by`).

4. What a skeptical PI or senior engineer would ask first
1. "If a user issues an unauthorized `/relay cancel`, and GitHub throws a transient 500 error when we try to reply, why do we mark the command as processed and permanently silence the rejection?"
   Evidence: `conversation.py` lines 358-362.

5. Documentation gaps
1. I needed to know how a repository administrator or maintainer could override the ownership block to clean up a reviewed task if the original requester is no longer available, and could not find it in the package.

6. What is done well
1. The PR closure logic in `_close_cancelled` is robustly idempotent and handles interrupted flushes safely without spamming duplicate comments.
   Evidence: `conversation.py` line 209 (`if not any(note in (c.get("body") or "") for c in self.gh.issue_comments(number)):`).

Verdict:
Ship with fixes. The core state handling, branch preservation, and idempotency of the PR closure logic are well implemented. However, deliberately swallowing network exceptions while marking a refused command as "applied" creates a frustrating edge case where the system silently ignores a user. Fix the `RelayError` suppression in the command loop and ideally patch the bypass gap for reviewed tasks missing a PR before shipping.
