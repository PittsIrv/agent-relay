## gemini-3.1-pro-preview

1. Correctness risks
1. Valid shell commands containing a `#` inside quotes will be truncated and fail to execute because the comment-stripping regex is overly broad. Evidence: `line = re.sub(r"\s+#\s.*$", "", line).rstrip()`
2. If an installation command starts with an environment variable assignment (e.g., `VAR=1 pipx ...`), `shlex.split(line)[0]` returns the variable assignment, causing the tool availability check to fail and bypassing installation. Evidence: `subprocess.run(f"command -v {shlex.split(line)[0]}", shell=True, env=env, capture_output=True)`
3. Grabbing the first command matching a prefix means the test will run the wrong command if the README lists an alternative or a help command (e.g., `relay add --help`) before the actual execution command. Evidence: `for line in readme_commands(): if line.startswith(prefix): return line`
4. A single step could hang for 9.9 minutes, silently eating the 10-minute total budget and causing the overall suite to fail the `commands <= 10` condition without triggering a clear timeout error. Evidence: `subprocess.run(..., timeout=600)` combined with `return 0 if not FAILS and commands <= 10 else 1`

2. Hidden assumptions
1. Assumes the README explicitly uses the exact uppercase placeholder `TASK` in the take command (e.g., it fails if the README says `<task_id>` or `TASK_ID`). Evidence: `re.sub(r"\bTASK\b", found[1], take)`
2. Assumes `relay status` outputs exactly a 10-character hex string preceded by whitespace and followed by "queued". Evidence: `found = re.search(r"^\s+([0-9a-f]{10})\s+queued", out, re.M)`
3. Assumes the README documentation relies specifically on installing via a GitHub URL; standard PyPI installs (e.g., `pipx install relay`) will not be recognized. Evidence: `if "git+https://github.com/" in line and ...`
4. Assumes the host environment's existing `gh` CLI session has the correct permissions and will not be impacted by running in the scratch repository. Evidence: `step("gh is signed in", "gh auth status", project, env)`

3. Design decisions you would challenge, and the alternative you would weigh
1. Manual regex removal of shell comments is brittle and prone to edge-case failures. Alternative: Do not strip comments; let the shell process the command normally since `/bin/sh` safely ignores trailing `#` comments and respects quotes.
2. Relying on string prefixes (`startswith(prefix)`) to guess which code block is the canonical step heavily limits how the README can be written. Alternative: Use hidden HTML comments in the README (e.g., `<!-- test: relay-add -->`) to explicitly tag which blocks the parser should execute.

4. What a skeptical PI or senior engineer would ask first
1. What happens to the test pipeline when we document a known error state or alternative workflow prior to the happy path in the README?
2. Does `sandbox.cleanup(slug)` completely reset the repository, delete issues, and remove branches if the script crashes halfway through a `git push`?

5. Documentation gaps
1. The package is missing the source or documentation for `e2e_github.py`, which is required to understand the scope of `sandbox.cleanup(slug)` and what specific API responses `sandbox.gh()` returns.

6. What is done well
1. The defense-in-depth against executing destructive actions on production repositories (`re.search(r"sandbox|scratch|e2e|test", slug...)`) is robust.
2. Thorough path and environment isolation prevents the test from accidentally passing using a globally installed version of the tool.

Verdict:
Ship with fixes. The automation of "README-driven development" is a highly effective way to prevent documentation drift, and the environment isolation is handled well. However, the regex-based shell comment stripping and the reliance on finding the *first* textual match for commands makes this test extremely brittle to normal documentation changes. Removing the regex comment stripper and adding a stricter anchor for identifying the canonical "happy path" commands is required before this can be merged.
