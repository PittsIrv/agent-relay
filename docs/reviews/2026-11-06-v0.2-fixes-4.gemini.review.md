## gemini-3.1-pro-preview

1. Correctness risks
1. A network failure during the second fetch in `take` triggers `unhold`, which will also fail if the network is down, leaving the task held indefinitely.
Evidence: `except Exception: tasks.unhold(store, task_id, cfg["worker"], task["epoch"], by=who)` in `take` requires pushing to the remote.
2. `unhold` blindly restores `past_prs` from `held_from`, which can erase concurrent valid updates (like a delayed `attach_pr` adding a superseded PR), potentially leading to duplicate `superseded` events on restart.
Evidence: `task["held_from"] = {k: copy.deepcopy(task.get(k)) ...}` in `hold` and `task[key] = value` in `unhold` overwrites `past_prs` completely.

2. Hidden assumptions
1. The remote Git server supports fetching unadvertised reachable commits by SHA, which is required if the `STATE_REF` advances before the local fetch executes.
Evidence: `git(self.repo, "fetch", "--quiet", "--no-tags", self.remote, tip)` in `landed`.
2. GitHub pull request numbers are globally unique and monotonically increasing for the repository, making them safe to use as absolute identifiers without checking the epoch.
Evidence: `if task.get("pr") == number: return "attached"` in `attach_pr`.

3. Design decisions you would challenge, and the alternative you would weigh
1. Reverting all cached keys in `unhold` destroys concurrent non-conflicting additions. Alternative: only revert the specific PR movement that `retire_pr` executed, rather than blindly restoring entire arrays like `past_prs`.
Evidence: `for key, value in previous.items():` restores a hardcoded snapshot from `held_from`.
2. Fetching twice in `interactive.take` to minimize the failure window during the `try` block adds synchronous latency. Alternative: perform a single fetch, and if it fails, queue the `unhold` action locally to retry automatically in the background.
Evidence: `git(repo, "fetch", ... start)` appears both before `tasks.hold` and inside the `try` block.

4. What a skeptical PI or senior engineer would ask first
1. "If a human runs `take` and their network dies, locking the task with a massive timeout, how do we forcefully release it?"
Evidence: `task["lease"] = {"worker": worker, "epoch": task["epoch"], "until": current + HELD_FOREVER, "human": True}` in `hold`.
2. "If `_retire` closes a PR, but GitHub is slow to reflect the state in subsequent API reads, will we spam duplicate comments?"
Evidence: `if not any(note in (c.get("body") or "") for c in self.gh.issue_comments(number)):` relies on immediate consistency of the comments API.

5. Documentation gaps
1. The package was sufficient.

6. What is done well
1. Using Git's native tree ancestry resolves the local-failure/pushed-state race effectively by leveraging the append-only data model.
Evidence: `return git(self.repo, "merge-base", "--is-ancestor", sha, tip, check=False).returncode == 0` in `landed`.
2. The idempotency guard explicitly checking the current PR safely isolates the delayed-attach interleaving.
Evidence: `if current.get("pr") == number: return  # Restored as the current PR` in `_retire`.

Ship. The fixes specifically address the blocking interleavings. The ancestry check correctly identifies landed commits regardless of local network drops, and the PR state check accurately prevents retirement of resurrected attempts. The remaining edge cases (such as `unhold` failures during a network drop or overwritten `past_prs` arrays) are either self-healing on restart or acceptable for an alpha tool with documented limits.
