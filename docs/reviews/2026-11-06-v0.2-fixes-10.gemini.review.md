## gemini-3.1-pro-preview

1. Correctness risks:
- `_note_superseded` returns silently if `pull.get("state") == "open"`. If GitHub's API is eventually consistent and reflects "open" immediately after `close_pr()`, the method completes without raising an exception. `_reconcile_retired` then executes `handled.add(key)`, permanently skipping the courtesy note for this clone. (Evidence: `if current.get("pr") == number or pull.get("merged") or pull.get("state") == "open": return` in `_note_superseded` combined with the `except DEFERRABLE` catch in `_reconcile_retired`)
- `_open_pr` eagerly calls `self._retire(number, task)` on refusal, which performs the close and note API calls but does not update the clone's local `retired.json`. The very next `flush` will redundantly call `_close_superseded` and `_note_superseded` again for the same PR. (Evidence: `self._retire(number, task)` in `_open_pr` and `handled = set(self._load("retired.json", []))` in `_reconcile_retired`)

2. Hidden assumptions:
- The design assumes `gh.pull()` will synchronously reflect a closed state immediately after `close_pr()` returns, otherwise the courtesy note gets skipped. (Evidence: Sequential calls to `_close_superseded` and `_note_superseded` inside the loop in `_reconcile_retired`)
- The design assumes redundant API checks across multiple workers are acceptable, as it relies on per-clone receipts to deduplicate the cleanup of shared global state. (Evidence: `handled = set(self._load("retired.json", []))` iterating over the shared `task.get("past_prs", [])`)

3. Design decisions you would challenge, and the alternative you would weigh:
- Tracking the completion of PR retirement in a per-clone local file (`retired.json`). Alternative: Track retirement completion directly in the durable shared state (e.g., adding `"closed": True` to the entry in `past_prs`), which would eliminate redundant checks across clones and remove the need for a local receipt entirely.
- Swallowing all `DEFERRABLE` exceptions in `_reconcile_retired` to allow issue narration to proceed. Alternative: If a PR close fails, deliberately halt the narration of the new attempt to minimize the window where a stale PR could be merged, strictly enforcing the "safety work first" principle.

4. What a skeptical PI or senior engineer would ask first:
- If a superseded PR fails to close due to a persistent error (like changed repository permissions), does it loop forever in `_reconcile_retired`, spamming the logs with deferrals on every heartbeat?
- If two clones reconcile the same abandoned PR simultaneously, could they both pass the existing comment check and post duplicate explanatory notes?

5. Documentation gaps:
- The package was sufficient.

6. What is done well:
- Decoupling PR retirement from issue narration by relying on the durable `past_prs` list is a robust and clean architectural fix.
- Distributing the cleanup so that any clone working on the task can clean up PRs left by a crashed worker adds excellent fault tolerance.
- The unit tests are highly specific and accurately reproduce the failure scenarios (like exceptions during note posting).

Verdict: ship.
The core bug that blocked the previous release—tying safety work to narration receipts—is completely and elegantly resolved by reconciling against shared durable state. The fix ensures that any active clone will clean up stale PRs, and it correctly prevents a failed note from blocking narration. While there are minor logic gaps around eventual consistency skipping notes and redundant API calls across clones, they fail safe (or at worst drop a courtesy comment) and do not compromise repository state. It is well-engineered and ready for an alpha release.
