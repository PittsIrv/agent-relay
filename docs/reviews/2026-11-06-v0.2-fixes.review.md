## 1. Correctness risks

1. **The attempt-scoped PR fix remains vulnerable to a stale PR-creation result (1.1, 3.2).** An epoch-1 `_open_pr` can be in flight while another worker retries and claims epoch 2. Its eventual `annotate` can then attach the epoch-1 PR to the new attempt. Once epoch 2 reaches review, merging that old PR can complete the task: `mark_done` checks the PR number but not its epoch. The supplied sequential retry test does not exercise this interleaving.  
   **Evidence:** `tasks.py`: `missing = {k: v for k, v in fields.items() if task.get(k) is None}`; `conversation.py`: `return tasks.annotate(self.store, task["id"], pr=number, pr_epoch=task["epoch"], pr_draft=draft)`; `tasks.py`: `if not task or task["status"] != "review" or task.get("pr") != pr:`.

2. **Synchronizing inside the attempt loop can now starve lease renewal (1.4).** The loop calls the entire synchronous GitHub synchronization path, including pagination, permission lookups, imports, PR checks and narration. Twenty requests approaching the 60-second timeout already exceed the default five-minute task lease. Another worker could reclaim the task while the original subprocess continues running. Adding a sync interval therefore does not establish a bounded cancellation latency.  
   **Evidence:** `worker.py`: `self.sync()` executes inside `while proc.poll() is None:`; `github.py`: `self.timeout = 60` and `MAX_PAGES = 20`; `tasks.py`: `def claim(store, worker, ttl=300, now=None, by=None, task_id=None, policy=None):`.

3. **Comment pagination can still lose commands at a timestamp boundary (1.5).** Sorting by update time repairs the original ordering mismatch, but the scan stops after 2,000 results and saves only the last timestamp. If more comments share that boundary timestamp, a subsequent exclusive `since` query can skip the remainder. There is no overlap window or explicit handling of a truncated timestamp group.  
   **Evidence:** `github.py`: `for page in range(1, MAX_PAGES + 1):` and `since=since, sort="updated", direction="asc"`; `conversation.py`: `newest = max(newest, comment.get("updated_at") or comment.get("created_at") or since)` followed by `self._save("sync.json", {"since": newest})`.

4. **Issue import remains permanently incomplete for a sufficiently large, stable open-issue set (1.6).** Pagination improves the first-page limit, but each synchronization restarts the same bounded scan. Issues beyond the first 2,000 results need not ever be visited while earlier results remain open. This is a scope limit, not complete pagination.  
   **Evidence:** `github.py`: `issues = self.pages(self.repo("/issues"), labels=label, state="open")`; `pages` always starts at page 1 and stops at `MAX_PAGES = 20`.

5. **Remote-marker deduplication is incomplete on long issue threads (1.9).** The marker search reads only the bounded comment listing. After local-cache loss, an event whose existing marker lies outside those pages can be posted again. The new test covers cache loss, but not a truncated thread.  
   **Evidence:** `github.py`: `return list(self.pages(self.repo(f"/issues/{number}/comments")))`; `conversation.py`: `if body and marker not in remote: self.gh.comment(...)`.

6. **Issue and PR creation still lack recovery from a successful remote operation followed by failed local recording (1.2, 3.1).** The ownership marker prevents the stated duplicate-*task import* race, but does not reconnect an orphan issue to its task. A later flush can create another issue. An accepted-but-unrecorded PR can instead leave repeated creation attempts failing without adopting the existing PR. Stale task objects can also cause duplicate issue creation despite the local lock.  
   **Evidence:** `conversation.py`: `number = self.gh.create_issue(title(task), self.issue_body(task))` precedes `tasks.annotate(...)`; `_open_pr` likewise calls `open_pr(...)` before annotation. Import merely skips bodies containing `"<!-- relay-task:"`.

7. **A failed `take` can restart work that was previously cancelled, blocked or awaiting review (1.10, 3.5).** The rollback always queues the task rather than restoring its prior state, and `hold` has already retired its PR. The supplied checkout-failure test starts from queued work, so it does not establish transactional behavior for the other accepted states.  
   **Evidence:** `tasks.py`: `if task["status"] not in ("queued", *REQUEUEABLE) and not expired:` followed by `retire_pr(task)`; `interactive.py`: the exception handler calls `tasks.update(..., status="queued", ...)`.

8. **The failed-`take` fix still leaves a crash window with a stranded hold.** A process death after `hold` but before configuration is recorded bypasses the exception handler; a store/network failure can also prevent the rollback itself. Such a task requires manual recovery because automatic claiming only expires `running` tasks, not `held` tasks.  
   **Evidence:** `interactive.py`: `task = tasks.hold(...)` occurs before the protected checkout/configuration block; `tasks.py`: `expired = task["status"] == "running" and task["lease"]["until"] < current`.

9. **Event-time start-SHA narration is only partially fixed (3.3).** Claims starting from a checkpoint snapshot its SHA, but claims starting from the base do not snapshot that base. Delayed rendering can therefore describe a subsequently changed base as the original starting commit.  
   **Evidence:** `tasks.py`: `start=(task.get("checkpoint") or {}).get("sha")`; `conversation.py`: the no-checkpoint rendering path uses `self.commit_link(task['base'])`; `tasks.update` permits `task["base"] = base`.

10. **An outage can permanently erase narration rather than merely delay it.** All events, including silent checkpoints, share a 50-event ring. Sufficient activity during an outage can evict unposted events even if the originating worker later returns. This is distinct from the explicitly accepted “worker never returns” limitation.  
    **Evidence:** `tasks.py`: `task["events"] = task["events"][-50:]`; `conversation.py`: `SILENT = {"checkpoint", "created"}` and the module contract says `"a GitHub outage only delays comments"`.

11. **Timeout containment is incomplete outside `GitHub.api` (1.3).** The API conversion is correct, but GitHub detection still directly runs a timed subprocess. Its callers are not supplied, so package-wide containment of `TimeoutExpired` cannot be established.  
    **Evidence:** `github.py`, `detect`: `probe = subprocess.run([*argv, "auth", "status"], capture_output=True, timeout=30)`.

## 2. Hidden assumptions

1. **Lease safety assumes a bounded difference between machines’ wall clocks.** A documentation warning acknowledges the dependency but does not establish a tolerable skew or recovery policy. This can be an alpha constraint, but it must be operationally specific.  
   **Evidence:** `tasks.py`: `current = time.time() if now is None else now` and comparison against `task["lease"]["until"]`; adjudication: `"Wall-clock leases → already documented"`.

2. **Dependency completion assumes the dependent’s base contains the dependency’s merged work.** Readiness checks status only, not ancestry or target-branch compatibility. The stated branch convention is therefore a correctness precondition rather than a convenience.  
   **Evidence:** `tasks.py`: `return all(dep is not None and dep["status"] == "done" for dep in deps)`; adjudication: `"dependents should target the branch the dependency merges into"`.

3. **Private-prompt handoff assumes intent is recoverable from the repository artifacts.** The privacy default is defensible for an alpha, but successful continuation is not established when the generated instruction merely asks another agent to infer the task from a diff.  
   **Evidence:** `interactive.py`: `parts = [f"Continue {owner}'s in-progress work on {where}{touched}"]`; subsequent instruction: `"Read .relay-handoff.md if it exists, inspect the diff against the base, run the tests, then finish the work."`.

4. **Narration ownership assumes worker identities remain stable and are not concurrently reused across independent clones.** Event publication is selected by worker ID, while serialization is only local to one filesystem. Neither identity lifecycle nor cross-clone exclusivity is established here.  
   **Evidence:** `conversation.py`: pending events require `ev.get("worker") == self.worker`; the lock is `(self.folder / "conversation.lock")` with `fcntl.flock(...)`.

## 3. Design decisions to challenge

1. **Retiring only the state link leaves obsolete PRs operational on GitHub.** An old PR still carrying `Closes #issue` can close the live task’s issue even when shared task state correctly refuses to mark the retry done. I would weigh explicitly superseding/closing old PRs and removing their closing keywords.  
   **Evidence:** `tasks.py`: `task.setdefault("past_prs", []).append(...)` then `task["pr"] = None`; `conversation.py`: `closes = f"Closes #{task['issue']}\n\n" if task.get("issue") else ""`.

2. **The rejection of any shared reconciliation mechanism is premature.** Checking comment markers addresses one crash window, not resource creation, stale attachment or abandoned narration. I would weigh a small attempt-keyed reconciliation record—or deterministic remote lookup and adoption—rather than necessarily a general-purpose outbox.  
   **Evidence:** adjudication: `"remote marker check removes the realistic duplicate case without another shared structure"`; `_flush` still performs remote creation before `tasks.annotate(...)`.

3. **Automatic non-draft fallback should be an explicit repository policy.** Matching the specific unsupported-draft phrase is an improvement, but an ordinary PR may trigger automation that a draft would not. I would weigh opt-in fallback or leaving the task in review with a clearly reported PR-creation failure.  
   **Evidence:** `github.py`: `pr = self.api("POST", self.repo("/pulls"), {**request, "draft": False})`; rendering promises `"A person reviews and merges the PR."`.

4. **A larger handled-ID ring is a bounded replay policy, not an at-most-once guarantee.** Editing an old command after its ID has been evicted can make it eligible again. I would weigh an explicit replay horizon with detectable truncation, rather than treating the choice as either 5,000 IDs or infinite shared state.  
   **Evidence:** `tasks.py`: `state["handled"] = handled[-HANDLED_KEEP:]`; adjudication: `"an unbounded set would grow shared state forever"`.

## 4. What a skeptical PI or senior engineer would ask first

1. **Can you show a two-machine trace that retries while PR creation is in flight, then merges the old PR after the new attempt reaches review?** That is the first acceptance test for the claimed attempt-isolation fix.  
   **Evidence:** adjudication: `"No real two-machine GitHub trace → agree; open"`; PR association uses the unrestricted `tasks.annotate(...)` path.

2. **What is the measured worst-case cancellation and lease-renewal latency under slow GitHub responses and a large synchronization backlog?** A polling interval alone does not answer either question.  
   **Evidence:** `worker.py`: the attempt loop directly calls `self.sync()`; `github.py`: `self.timeout = 60`.

3. **Which exact commit and tree did the successful check validate, and what reproducible test demonstrates detection of check-induced changes?** The package shows consumption of the verification fields, not their production.  
   **Evidence:** `conversation.py`: `verification.get("snapshot_changed_during_check")` and `short(verification.get("input_sha"))`.

4. **What is the supported recovery procedure after GitHub accepts an issue or PR but the client times out before recording its number?** This must cover adoption, duplicate cleanup and preservation of collaborator commands.  
   **Evidence:** `conversation.py`: remote `create_issue(...)` and `open_pr(...)` calls precede state annotation.

## 6. What is done well

1. **The permission cache now implements bounded expiration and avoids caching non-404 API failures.**  
   **Evidence:** `github.py`: `time.monotonic() - cached[1] < PERMISSION_TTL`; `if "404" not in str(exc): raise` occurs before cache assignment.

   **Evidence:** `except subprocess.TimeoutExpired as exc: raise RelayError(...) from exc`.

   **Evidence:** `interactive.py`: `if known and tree == previous.get("tree"):`; after the final snapshot, `tree = output(repo, "rev-parse", f"{sha}^{{tree}}")`.

4. **The added tests target concrete historical failure cases rather than only happy paths.**  
   **Evidence:** `test_retry_after_review_gets_a_new_pr_and_old_merge_does_not_finish_it`, `test_lost_local_cache_does_not_duplicate_comments`, and `test_failed_take_returns_the_task_to_the_queue`.

**Verdict: do not ship this revision yet.** Several fixes repair their narrow reported cases, but stale PR attachment can still complete the wrong attempt, and synchronous GitHub work inside the attempt loop can undermine lease ownership. Those are core correctness failures, not limitations that an alpha disclaimer resolves. Clock skew constraints, privacy-default handoffs, branch conventions, originating-worker narration, POSIX-only support, bounded history and legacy-task behavior could be acceptable disclosed alpha limits. Before release, fence PR association and completion by attempt, prevent synchronization from starving heartbeats, make truncated scans detectable and recoverable, and provide targeted interleaving tests plus the outstanding real two-machine GitHub trace.
