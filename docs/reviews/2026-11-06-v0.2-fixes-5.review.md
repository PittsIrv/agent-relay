## 1. Correctness risks

1. **A failed take can strand a task in `review` without a PR if PR creation was still in flight.** Start with a review task at epoch E whose PR has not yet attached; `hold` increments the epoch; the delayed attachment is rejected; `unhold` restores `review` but retains the incremented epoch. Subsequent flushing cannot open a replacement because the last review event still belongs to E.  
   **Evidence:** `task["epoch"] += 1`; attachment rejects when `task["epoch"] != epoch`; rollback restores only `task["status"]`; PR creation requires `last.get("epoch") == task["epoch"]`.  
   The new overlap test does not cover this sequence: it finishes the worker and obtains `before["pr"]` before holding. Add a test that pauses PR creation before attachment, holds, rejects the late attachment, rolls back, and verifies eventual PR publication.

2. **Handing back a held task with an existing PR can erase the new verification result.** `update` installs the supplied verification before retiring the prior attempt’s PR, and retirement deletes verification. Consequently, the review event can record no check result even when the caller supplied one.  
   **Evidence:** `if verification is not None: task["verification"] = verification` precedes `retired = retire_pr(task) ...`; `retire_pr` executes `for key in ("verification", "pr_epoch", "pr_draft"): task.pop(key, None)`.  
   Retire old-attempt metadata before installing new-attempt verification, and test that the returned task and review event retain the supplied result.

3. **Pagination exhaustion is silently presented as a complete result, undermining marker-based duplicate prevention.** If a retirement marker lies beyond the page cap, `_retire` can post another note even without two clones racing. Issue adoption has the corresponding risk when the owned issue is beyond the cap.  
   **Evidence:** `for page in range(1, MAX_PAGES + 1)` has no exhaustion error; retirement tests marker absence using `self.gh.issue_comments(number)`; issue adoption searches `self.gh.labeled_issues()`.  
   This is a bounded-data limitation, but the supplied documentation identifies only simultaneous-clone retirement-note duplication.

## 2. Hidden assumptions

1. **Retirement safety depends on superseded PRs never becoming eligible for attachment again, but attachment does not enforce that invariant.** The revised hold path removes one route to restoring a retired PR; it does not make retirement a checked terminal property of the PR number.  
   **Evidence:** Successful attachment ends with `task.update(pr=number, pr_epoch=epoch, pr_draft=draft)` without checking `past_prs`; `past_prs` is checked only inside the rejection branch.

2. **The revised concurrency guarantee assumes participating clones use compatible hold semantics.** A clone running the previous implementation can still unlink and schedule retirement during a reversible hold. No supplied operating instruction requires a coordinated upgrade.  
   **Evidence:** The diff replaces `old = retire_pr(task)` inside `hold` with a status-only snapshot and preservation of the PR link.

3. **Recovery of externally visible work assumes the originating clone eventually runs again.** This is now stated, but no operational bound or mechanism ensures it.  
   **Evidence:** “If it never runs again, a superseded PR may stay open; close it by hand.”

## 3. Design decisions to challenge

1. **I would separate lease fencing from PR-publication identity rather than make failed checkout rollback advance both through one epoch.** Fencing stale workers is necessary, but the current rollback leaves publication events referring to an epoch that can no longer publish. An alternative is an explicit publication generation, or a rollback transition that safely re-establishes publication eligibility.  
   **Evidence:** `hold` increments `task["epoch"]`; `unhold` leaves it incremented; `_flush` requires the review event’s epoch to equal the task epoch.

2. **I would separate clearing old verification from retiring the old PR.** A helper that retires a PR should not implicitly destroy newly supplied attempt evidence. Explicit attempt-scoped metadata would make the transition easier to audit.  
   **Evidence:** `retire_pr` clears `"verification"` together with `"pr_epoch"` and `"pr_draft"`.

3. **I would weigh a repository-visible retirement queue with explicit terminal eligibility against owner-local event replay.** This need not guarantee exactly-once comments, but it would permit another worker to finish an abandoned retirement and make the irreversible transition explicit.  
   **Evidence:** Pending events require `ev.get("worker") == self.worker`; the documentation says an abandoned clone can leave a superseded PR open indefinitely.
